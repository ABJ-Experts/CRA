# M11-04 CI SBOM intake and build status

This plan records the M11-04 implementation sequence. The user-approved scope is GitHub Actions first, then GitLab CI and Azure DevOps, with local provider simulators and an external sandbox checklist. CI status remains nonpassing until a policy owner defines build criteria. The architecture and operational contract are in `docs/architecture/m11-04-ci-sbom-gates.md`.

## Execution

1. Characterize the M3 CI upload, connector vault, tenant scope, and existing status paths. Preserve `/api/v1/ci/sbom-uploads` and other M1–M10 contracts.
2. Write failing contract and application tests for client-forged provider identity, tenant substitution, ref mismatch, fork/PR context, duplicate run/attempt, concurrent binding edits, premature pass, and provider outage.
3. Extend feature-first Zod contracts so CI bodies contain only binding/run reference and file metadata. Owner binding creation requires connector, stable repository/project/pipeline IDs, exact allowed ref, product, release, and CI credential. Add a narrow provider verification adapter per vendor using the connector vault.
4. Add the minimal additive SQL binding/run records and atomic M3 reservation/finalization correlation. Use org-scoped foreign keys, idempotency and optimistic version checks, explicit grants, RLS, and pinned function search paths. Preserve existing evidence and migrations.
5. Add thin Nest owner and CI routes; status is `pending`, `error`, or `policy_not_configured` under policy `unconfigured`. Add bounded owner run history without CI secrets.
6. Add parsed browser gateway, operational owner UI, and GitHub/GitLab/Azure templates that consume an existing SBOM. Separate upload success from nonpassing build status.
7. Verify per-provider fixture contracts and local upload → processing → status; run SQL auth/transaction tests, Playwright accessibility/critical journeys, and `pnpm verify`. Record migration, rollback, API/schema, screenshots, BRD-to-test evidence, and residual provider sandbox gaps.

## Preserved boundaries

No new SBOM generator/parser or vulnerability policy. No GitHub PAT path. No client-supplied trusted flag or product/release authority. No automatic passing gate from successful ingestion. No reset of local or customer data. Do not claim a real-provider sandbox result from a simulator.
