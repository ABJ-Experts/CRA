# M12-06 notification burst batching

## Scope and preserved contracts

FR-WF-010 (BRD v2.0, p35) asks for useful summaries when a large feed update creates a notification burst. The opt-in feature groups eligible, noncritical in-app events and immediate optional email within two minutes; an email batch contains at most 100 source events. M12-03 daily/weekly digests, M12-04 source-owned feed and read state, and M12-05 Slack/Teams routing remain separate. Regulatory deadlines, approvals, delivery failures, and high/critical events never wait for a burst window. Source events, delivery outcomes, and actionable links remain individually auditable.

Preserve `/api/v1`, HttpOnly cookie paths, ES256/JWKS and session revocation, frozen auth action signatures, permission merge order, menu and mock behavior, all existing route defaults, and the default event feed response. No generic event bus, streaming platform, new provider, or new source ledger is introduced.

## Concrete problem and why not simpler

`notification_dispatches` deduplicates optional retry handoff by source and recipient. `notification_digest_batches` persists daily/weekly membership of at most 100 dispatches, but immediate mail sent one message per source event. `m1204_feed_rows` renders each source event separately, so a large ingestion can create a repetitive inbox. Chat already keys source revisions and carries high-severity, deadline, or approval classes; batching it would delay actionable work.

A presentation-only grouping would not reduce email, and a new generic notification ledger would duplicate M2/M5/M6/M8/M9 source history. Extend the existing optional dispatch and batch records for email, and compute feed summaries from currently authorized source rows. No new table is needed.

## Selected patterns and rejected patterns

- **Existing adapter boundary:** source-specific SQL bridges derive immutable event class/revision from source records. A dedicated burst worker runs alongside the existing direct/digest workers in the notification-dispatch process and uses notification-owned queue and SMTP adapters. The trigger is real provider/database variation and durable lifecycle; remove the burst-specific worker when short-window email delivery is retired.
- **Persisted state with a lease fence:** a frozen dispatch-ID array and prepared sent-member array distinguish intended membership from the actual authorized payload. SQL transitions, compare-and-swap versions, and audit inserts share transactions. The trigger is recovery after restart or provider ambiguity; remove these fields if burst delivery is retired.
- **Read-time projection:** `m12_06_feed_rows` is the optimized authorized source projection. The existing M12-04 function delegates to it with the same signature and row shape, so default, grouped and filtered feeds share current visibility rules. A two-minute cohort is computed for the current actor and organization; no stored title/content copy is needed.

Rejected: a new event bus, per-channel batch tables, browser-side grouping after pagination, a global singleton holding pending events, and in-channel approval actions. The direct source-specific SQL and existing worker patterns meet the current requirements with fewer consistency boundaries.

## Data and tenant boundaries

Browser requests derive actor and organization from the verified session. Admin policy changes require admin role and `can_edit_organization`, an expected version, an idempotency key, and an audit fact. Workers carry recorded organization, recipient and source IDs; every service-role query scopes organization first. Existing email retry uniqueness remains `(organization, source type, immutable source event UUID, original recipient)`, with email as the implicit channel. Current M5/M8/M9 sources create a new event UUID for each semantic generation; `event_class` and `semantic_revision` record that identity, but do not permit a second dispatch for the same event UUID. This preserves M12-03 bridge conflict targets. Semantic batching is separately keyed by organization, recipient, event class and two-minute ingestion window. A reopened finding emits a new SLA alert event; distinct approvals and regulatory stages retain their source-owned event identities and stay direct.

An organization starts disabled. Enabling records a start timestamp, so historical feed rows are not retroactively grouped. Eligible optional email is reclassified to a burst-pending status; daily/weekly/off preferences are unchanged. A two-minute window or a 100-member cap freezes membership in an existing digest batch with `batch_kind=burst`. A singleton returns to its original immediate format. On opt-out or preference change, unattempted members are reclassified under current policy. Attempted or uncertain sends are never automatically replayed. The source ledger and frozen batch membership are retained; SQL completion updates members, batch outcome, and audit atomically. SMTP acceptance cannot be transacted with PostgreSQL, so an expired post-attempt lease remains uncertain for manual review.

Use a CLI-generated additive migration, generated database types, pinned function `search_path`, explicit RPC grants, non-forced RLS and org-first indexes. The extended organization settings and dispatch tables already participate in tenant export; batch execution state is intentionally excluded. All three tables remain covered by organization cascade purge. Do not reset data or mutate an unrelated Supabase project.

## API boundary contracts

`@repo/contracts/notifications` owns strict burst-policy input/output, grouped-feed query and response, and filtered inbox schemas; trusted types use `z.output`. `GET/PATCH /api/v1/notifications/burst-policy` are admin-scoped. `GET /api/v1/notifications/feed` defaults to the unchanged event view; `view=grouped` returns authorized summaries plus ungrouped critical/source rows. A filtered event view accepts either a frozen email `batchId` or an event-class/window pair, and validates that the pair is complete. Every JSON response is parsed by `@ZodResponse`; every browser request supplies the appropriate input and output schemas. The worker adapter parses untrusted RPC output before constructing SMTP payloads.

Summary counts and previews are computed only from currently visible members. The preview is bounded and explicitly marked truncated; the link opens a permission-checked filtered inbox, never a raw source ID list. Source items keep their existing destination resolver and mark-read contract. Feed cursors bind actor, organization, view and filters to prevent reuse across scopes.

## Frontend logic and rendering

The functional `NotificationCentre` uses its existing gateway and query lifecycle. It renders a compact summary row with event class, visible count, unread count, window, outcome and an `Open events` action. The filtered view uses ordinary source rows so deep links and bounded mark-read remain familiar. An organization settings control exposes opt-in and its current version. Loading, empty, forbidden, offline, conflict and retry states retain unsaved input, focus and readable text status. Use existing semantic tokens, `cn()`, shared UI subpaths, locale dates and reduced-motion behavior. No dashboard or decorative graph is added.

## Failure modes and observability

- Duplicate bridge calls, out-of-order source events and concurrent schedulers must produce one dispatch per semantic revision and at most one active batch membership. Late arrivals after a frozen window enter a later batch index; they are not dropped.
- Revoked membership, product permission, route, source status, preference or opt-in cancels or recomputes an unsent payload before outbound bytes. Empty authorized membership cancels the send. Critical and high-severity work continues on independent direct paths.
- Provider throttling and outage use bounded retry and tenant-fair claims. A timeout after possible provider acceptance is uncertain, not delivered or safe to auto-replay. Safe codes and aggregate counts are logged; titles, credentials, tokens and provider responses are not.
- Feed pagination, grouping and filtered links recheck current authorization, including after an organization switch. A forged, expired or cross-tenant filter returns a safe error or empty result without disclosing membership.
- Disablement drains unattempted burst work. In-flight attempts are reviewed before an older worker version is restored; the additive schema and source history remain.

## Tests, rollout and rollback

Start with failing characterization and contract tests. Cover SQL RLS/grants, source uniqueness and reopen cycles, batch size/window, singleton, concurrent claims, permission and preference revocation, source deletion, provider throttling, uncertain leases and restart. Cover mixed critical interleaving and multiple tenants with a 1,000-event same-key burst; target at least 90% fewer outbound messages. Benchmark read p95 below 400 ms and p99 below 1,000 ms at realistic local load, recording the actual sample and limits. New or materially changed modules require at least 80% branch/function/line/statement coverage.

Run focused tests, database lint/diff, generated-type parity, `pnpm verify`, `pnpm test:live`, Mailpit, auth/navigation/organization-switch regressions, and Playwright MCP journeys with development owner credentials. Capture desktop/mobile screenshots and keyboard/reduced-motion checks. Deploy schema, types, API/worker, then web; enable one organization at a time. Roll back by disabling batching, draining unattempted work, reviewing uncertain attempts, then restoring old application code. Keep the additive migration and audit/source rows; correct schema forward rather than resetting data.

## Schema, API and operational runbook

- Schema: `apps/infrastructure/supabase/migrations/20261005055356_m12_06_notification_bursts.sql` extends organization settings, dispatches and digest batches; `20261005055904_m12_06_reopened_sla_revision.sql` versions new M5 breach cycles without changing historical events; `20261005081213_m12_06_burst_performance.sql` replaces the schedule/prepare paths with scoped set-based work under the local statement timeout. Both generated database-type copies are updated by `pnpm --filter infrastructure run db:types`.
- Contracts/API: `packages/contracts/src/notifications/schemas/notification.schema.ts`; `GET/PATCH /api/v1/notifications/burst-policy`, `GET /api/v1/notifications/burst-batches`, and `GET /api/v1/notifications/feed?view=grouped` or its scoped event filters. The default feed and source row contract remain compatible.
- Worker: build the API, then run `pnpm --filter api run worker:notification-dispatch` with the existing SMTP configuration; `--once` is available for an operational cycle. The process runs direct email, digest, burst and chat workers in parallel. A 30-second cycle plus the two-minute window sets normal optional-email dispatch timing. Monitor audit actions `notification.burst_*`, pending and leased counts, `safe_error_code`, and provider acceptance; investigate `delivery_uncertain` before any manual replay.
- Rollout: apply the additive migration on a verified CRA database, regenerate types, deploy backend/worker before web, then enable one organization at a time through the versioned admin control. Leave other organizations disabled. Rollback disables the switch, allows unattempted members to reclassify, and requires review of leased/uncertain sends before restoring an older worker. Retain additive columns, frozen membership, source rows and audit; correct forward without a data reset.

The Supabase MCP currently exposes only unrelated ERP projects. Local catalog inspection and transaction-scoped SQL testing targeted the confirmed `supabase_db_cra` container; no unrelated remote or production project was queried or changed. All three M12-06 migrations are present in the local migration ledger. The extended tables retain enabled, non-forced RLS; the private RPCs, indexes, constraints and triggers are present.
