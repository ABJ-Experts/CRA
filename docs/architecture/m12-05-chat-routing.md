# M12-05 Slack and Microsoft Teams alert routing

## Scope and preserved contracts

M12-05 routes selected high-severity alerts, deadline warnings, and approval prompts to customer-managed Slack and Microsoft Teams destinations. The content is intentionally generic: event class, severity, time, and a CRA application link built from verified source IDs. The link requires a current CRA session and source permission. A channel test contains synthetic text and a confirmation code, never a real record.

M12-03 mandatory email and M12-04 in-app delivery remain independent. This change does not alter `/api/v1`, auth cookies, ES256/JWKS, frozen auth actions, permission merge order, source workflow states, existing mail preferences, menu contracts, or mock passthrough. It adds no chat approval action, inbound bot callback, hosted provider, evidence attachment, report draft, or automated disclosure of findings.

## Concrete problem and why not simpler

M2, M5, M6, M8, and M9 already commit source events and outbox records, but none has a per-channel chat attempt or destination binding. Sending directly from each source worker would duplicate provider calls and lose a consistent way to handle route changes, restart ambiguity, tenant-fair rate limits, and admin retry. M11 `ConnectorPort` owns product/release synchronization; its signed outbound webhooks send CRA envelopes and cannot carry Slack bot or Teams Workflows payloads. The direct solution therefore uses those durable source records and two notification-owned tables, without a generic event bus or another worker process.

## Selected boundaries and alternatives

- Source-specific SQL projections map only the supported event kinds to `high_severity_alert`, `countdown_warning`, and `approval_prompt`. The bridge uses source event identity and route activation time; a new revision is a new logical event. A narrow M6 `approval_requested` event is committed when a report revision becomes actionable, because that state was previously derived rather than durable.
- `notification_chat_channels` stores explicit product scope, event classes, mode, version, challenge verification, activation time, and an AES-GCM envelope. The envelope uses M11 vault key material with AAD scoped to organization, channel, and credential revision. A productless M6 deadline requires an explicit `includeOrganizationWide` choice. `notification_chat_deliveries` stores one bounded attempt state per route/source/revision; it is not a legal filing or receipt acknowledgement.
- The application use case owns the authenticated actor and organization. A notification repository owns scoped SQL and encrypted credential access; four provider adapters own Slack webhook/bot and Teams Workflows/proactive-bot protocol differences. The notification worker runs beside existing email/digest cycles with independent failure handling. Removing chat routes and stopping chat claims safely removes these adapters without changing source producers.

Rejected: placing chat rows in sync-oriented `connectors`, reusing M11 signed webhook endpoints, creating one provider-specific table per mode, adding an installation OAuth flow, and adding a generic orchestration platform. Those approaches introduce unrelated state or cannot meet the currently required payload and delivery semantics.

## Tenant, security, and transaction boundaries

Tenant admin status plus `can_edit_organization` is required for configuration, test, confirmation, enablement, and retry; audit permission is required for delivery diagnostics. Product IDs are explicit, belong to the active organization, and are checked again when a delivery is prepared and immediately before outbound bytes. A route edit or disable cancels unsent work. Source records, archived/deleted state, approval eligibility, route version, and tenant scope are rechecked for each send; service-role calls take `organization_id` first. A channel binding is enabled only after the admin sees a synthetic challenge in the destination and confirms its code.

Source events are transactionally durable at their transitions. The bridge inserts chat deliveries idempotently using `(organization, channel, source kind, source ID, source revision)` and does not replay old confidential events when a route is created. Configuration, confirmation, retry, state changes, and their audit facts commit together through versioned SQL RPCs. The worker records an attempt before calling a vendor. If a lease expires without a completion, the state becomes `uncertain` and requires admin review; a possibly accepted request is not automatically resent. Vendor success means `provider_accepted`, never inbox receipt. No provider credentials, webhook query strings, raw provider response, message body, or unnecessary personal content enters public JSON, audit changes, logs, or delivery diagnostics.

The additive migration uses non-forced RLS, explicit service-role grants, `public.users.id` foreign keys, pinned SQL `search_path`, indexes for bounded tenant claims and history, and tenant export/purge registration. Regenerate both database type copies through the repository script. Existing organizations begin with no chat route enabled.

## API, rendering, and vendor behavior

Feature-first `@repo/contracts/notifications` schemas parse each consumed path, query, body, and successful JSON response. The API exposes bounded channel configuration/test/confirm/enable and delivery-list/retry routes under `/api/v1/notifications`. Web callers provide input and response schemas through the existing transport, scope query keys by verified user and organization, and keep unsaved non-secret drafts after conflicts or outages. The organization panel uses semantic tokens, shared UI subpaths, keyboard focus, text status, and compact forms. Notification refresh failure never blocks triage, evidence, or reporting.

Slack incoming webhooks are destination-bound secrets. Slack bot mode requires a customer-installed bot with `chat:write` and access to the target channel; `chat:write.public` is needed only if the customer chooses to post to public channels the bot has not joined. Teams Workflows mode supports a customer-created **Anyone** webhook trigger; the customer should assign a co-owner to prevent an orphaned flow. Teams proactive bot mode requires the customer-installed public-cloud app and a conversation reference that passes the synthetic test. Government cloud endpoints and other Teams trigger authentication modes require separate validation before support. Provider hosts are allowlisted, DNS is pinned to a public address, TLS checks the hostname and certificate, redirects are refused, and requests/responses have size and time bounds. Slack JSON `ok:false` is a failure even with HTTP 200; 429 and retryable 5xx use bounded delay, while removed destination or revoked credentials remain visible for repair.

## Verification, deployment, and rollback

Start with failing contract, SQL, API, worker, adapter, and UI tests. Cover tenant substitution, changed product/source permission, route and credential change, duplicate/revised/out-of-order events, two workers, timeout after possible acceptance, lease expiry, rate limits, provider 4xx/5xx, DNS/TLS/redirect failure, mention escaping, safe links, synthetic binding, admin retry, and the independence of mandatory email/in-app delivery. Require at least 80% branch/function/line/statement coverage for new or materially changed modules. Run focused suites, SQL tests and lint/diff, `pnpm verify`, `pnpm test:live`, auth and organization-switch/navigation regressions, Playwright MCP browser journeys, accessibility checks, and read p95/p99 measurements against 400/1000 ms targets.

Deploy schema and generated types before API/web, then start the updated notification worker. Configure a destination disabled, send and confirm the synthetic challenge, review the generic disclosure preview and product/event scope, then explicitly enable. Slack and Teams credentials, webhook URLs, and the `CONNECTOR_VAULT_KEYRING` belong in deployment secrets; `APP_URL` must identify the CRA application origin. Rotate vault keys only after the maintenance command confirms all retained envelope references are readable and rewrapped. To roll back application code, stop chat claims and retain additive tables, attempt history, and audit facts. Future schema corrections require forward migrations; do not reset organization data.
