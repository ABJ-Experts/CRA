# M13-01 — Durable, redacted audit events

## Scope and preserved contracts

The implemented outcome is an authoritative, durable audit fact for the migrated security-critical domain operations, with distinct facts for failed security attempts and unresolved intent for externally uncertain outcomes. The existing `public.audit_logs` table remains the append-only sink; historical rows are retained as historical evidence, not silently upgraded or fabricated. M13-02 hash chaining, M13-03 search/export, a general AI gateway, and raw confidential content in audit records are outside this slice. The operation register names each current route and worker's evidence source and makes the four reviewed auth availability exceptions explicit.

Preserve `/api/v1`, ES256/JWKS verification, the narrow `cra_rt` refresh cookie, frozen auth-action signatures, zero session epoch skew, permission merge order, source-owned domain decisions, and the current mail/auth availability semantics. An audit-store outage must fail a security-critical database mutation before it reports success. During the compatibility rollout sign-in and refresh remain available with an explicit degraded signal; that is a known evidence gap, not a claim of complete capture.

## Concrete problem

`apps/api/src/audit/audit.service.ts` inserts through the service role in an unawaited, nonthrowing task. Member and role use cases call it after repository writes (`apps/api/src/users/application/member-use-cases.ts` and `apps/api/src/permissions/application/role-use-cases.ts`), so a successful response can lack its audit row. The current schema in `20260809091300_audit_logs.sql` has no actor type, stable retry identity, first-class correlation, outcome, or explicit redacted before/after envelope. In contrast, the M9 supplier-field decision SQL (`20260923114524_m9_05_field_decision_row_lock_fix.sql`) and M12 notification delivery SQL (`20261001143000_m12_03_notification_delivery_foundation.sql`) write audit facts within their domain transactions. Adding a second API log to either would duplicate evidence.

The [operation register](m13-01-operation-register.json) inventories every Nest `POST`, `PUT`, `PATCH`, and `DELETE` method and semantic worker implementation. `scripts/architecture/audit-operation-coverage.mjs` discovers the route and worker surface independently and fails a missing, duplicate, stale, or unresolved registration, a missing evidence file or source symbol, and any new best-effort exception outside the four reviewed auth routes. The register now maps 319 routes: 286 transactional audit, 11 external intent, 14 read-only commands, four durable job histories, and four explicit best-effort auth availability exceptions. Of 34 semantic worker files, 32 use durable job/delivery history and two write transactional audit. Five representative RPCs are also registered. These classifications are grounded in cited symbols and focused SQL tests; the gate does not enumerate every SQL function or prove each function body semantically safe.

## Why not simpler? Selected patterns

Adding more calls to `AuditService.log()` is the direct option. It cannot share a transaction with the state change and cannot distinguish a successful write from a lost best-effort event. Replacing its signature with a throwing method would unexpectedly break noncritical callers. The selected design keeps that compatibility path and adds explicit, organization-scoped transactional RPC writers for critical member/role changes, plus narrowly typed event-envelope creation for new facts. The existing application ports own the mutation contract; Supabase adapters implement them. The same transaction records changed state and one event keyed by a stable operation identity. If these workflows cease to be persisted, remove the RPC adapter rather than introducing a general command bus.

The existing source-owned SQL writers remain authoritative. AI inference and review reference the retained run, evidence version and field artifact rather than copying prompt, source passage or result content into audit JSON. Auth provider transitions use a durable intent/outcome where provider and PostgreSQL cannot share a transaction. Neither a generic event bus nor a new audit table solves the current consistency problem.

## Data and tenant boundaries

- Verified Nest identity supplies the actor and organization. Service-role methods accept the organization first and filter every tenant record. Before tenant identity exists, only the server may assign the protected security scope; a request body never supplies it.
- New envelope fields are additive and nullable for legacy rows. New-version rows require a stable event key, one actor type and stable actor ID, explicit scope and outcome, valid correlation ID, redaction version and safe metadata. Retry with an identical identity/payload returns the existing fact; an identity reused for a different payload conflicts. Organization and security-scope uniqueness are separate.
- Redaction precedes hashing or persistence. Allowlisted projections retain operational IDs, safe enum values and references; passwords, OTPs, cookies, access or refresh tokens, API keys, signed URLs and confidential AI content become a marker or approved protected reference. Low-entropy secrets are never retained as hashes.
- Actor identity survives user pseudonymization through a stable ID; copied email is not a required new-envelope field. `audit_logs` remains non-forced RLS and append-only for application roles. Use pinned SQL `search_path` and explicit function grants.
- Successful domain mutation and audit insertion commit together in one PostgreSQL transaction. An external identity provider or SMTP acceptance cannot be made exactly-once with PostgreSQL; intent and outcome distinguish the uncertainty rather than claim atomic external delivery.

## API boundary contracts and frontend

`@repo/contracts/audit` owns versioned event schemas and parsed `z.output` types. Existing public feature routes and response shapes remain compatible. Any new JSON status endpoint requires parsed input and successful response schemas in that feature, `@ZodResponse` in Nest, and `schema` in a web caller. No new audit viewer or dashboard is part of M13-01; the existing functional sign-in, role and supplier-review surfaces provide the browser regression journeys. Their current loading, forbidden, conflict, retry, focus and locale-date behavior remains intact. A new React logic class is unnecessary.

## Failure modes and observability

- Database or audit trigger failure rolls back security-critical state and returns a safe unavailable or conflict response. A duplicate event key with a changed redacted envelope is an optimistic conflict.
- Provider success followed by missing outcome is visible as unresolved intent. An operator must reconcile provider evidence before recording any later conclusion; no automatic replay or reconciler is implemented here.
- Sign-in and refresh are a bounded compatibility exception: they remain available during audit failure, while the readiness response reports `audit: false` and operators investigate the gap. This signal must not include credentials, tokens, email addresses, prompts or raw provider errors.
- Invalid correlation IDs are rejected or replaced by a server-generated value before persistence. Forwarded IP is trusted only from configured proxy addresses. An unknown forwarding hop falls back to the direct peer address.
- Revoked membership or product access fails closed before a tenant-scoped mutation or AI review. Event reads and future exports must recheck authorization independently of the captured actor ID.

## Tests, rollout and rollback

Write failing characterization tests before changing the writers. The coverage gate tests missing, duplicate, stale and missing-evidence registrations. Contract and policy tests cover event identity, redaction, actor/scope and malformed correlation. Real local PostgreSQL tests cover transaction rollback, RLS/grants, tenant and product substitution, concurrency, duplicate keys, audit-store outage and pseudonymized actors. Auth tests cover success/failure, MFA challenge, revocation and permission changes. AI tests cover model/prompt/reference/reviewer metadata with secret canaries. Playwright checks existing critical journeys and screenshots; `pnpm verify`, database lint/diff and applicable live-stack regressions complete the gate. New or materially changed modules target at least 80% branch, function, line and statement coverage.

Deploy additive schema and generated types, then transactional API/worker writers, then enable enforcement and audit health monitoring. Verify that the previous API can run on the expanded schema. Rollback disables new enforcement and drains or reviews unresolved intents before restoring an older worker; preserve additive columns and rows and correct schema forward. Do not reset local data or contact an unrelated Supabase project. Available Supabase MCP projects at planning time were unrelated ERP projects, so local `cra` tooling is the database verification path.

Invitation creation uses `m13_01_create_invitation_atomic` to commit the pending row and redacted v2 `invitation.created` event together. The mail send and M1 onboarding delivery fact follow it. On a failed mail attempt, `m13_01_cancel_failed_invitation_delivery_atomic` revokes only the original token-hash version and writes a separate cancellation fact, allowing a fresh create retry. A concurrently rotated resend or accepted invitation is left untouched. If the cancellation RPC itself is unavailable, the generic create error remains, the pending row needs an authorized manual resend/review, and readiness/operational logs must show the recovery failure. Provider acceptance followed by a thrown error remains uncertain; an invalidated link may need a new invitation.

## Coverage closure design

The follow-up objective is to replace every `legacy-unverified` route and worker entry with a traced authority. The direct solution is to point to the existing source-owned SQL audit insert or durable job/delivery ledger when that source already commits with the state transition. A new writer is justified only when a real state change has no such source. The operation register remains the static coverage boundary; its gate rejects unresolved entries rather than accepting a controller file as evidence.

The only new persistent behavior is a narrow projection into the existing `audit_logs` table for confirmed source gaps. Each projection runs in the same local PostgreSQL transaction as its source event or state change, carries server-derived scope and safe references, and does not copy credentials, provider payloads or confidential content. No generic table trigger, event bus, second audit store, or replay of external side effects is introduced. Source-owned M1–M12 audit rows remain authoritative where they exist; job leases are represented by durable job history rather than one audit row per heartbeat.

Failing SQL tests precede each forward migration and verify same-transaction rollback, idempotent retry, authorization scope and redaction. The architecture test must fail on any unresolved route or worker. A previous API can run with additive audit projections; rollback restores prior workers only after pending provider intents are reviewed and leaves additive schema/data intact. Sign-in and refresh retain the explicitly approved availability exception during an audit-store outage; readiness reports degradation, and an operator must reconcile the evidence gap from verified sources.

### Profile lost-response replay follow-up (2026-10-06)

The RPC first checks the verified actor's organization membership and locks the source row, then replays a matching key only when the supplied fields still match the committed row and no later profile revision occurred.
