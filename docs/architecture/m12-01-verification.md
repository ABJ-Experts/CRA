## Deployment, backfill, and rollback

Deploy additive migrations and CLI-generated database types before the API, then the web app. No task-source backfill or event worker is needed because reads project current source records. The five workflow tables store routing and command/audit metadata only. Keep prior API/web deploys available for rollback; a prior app can run with the new tables retained. Do not drop routing or audit evidence as part of rollback. Source approvals, acceptance, and remediation still run only through their existing modules.

For local recovery, verify `supabase status` points to `http://127.0.0.1:54321`, run `pnpm --filter infrastructure run db:lint`, `pnpm verify`, and `pnpm test:live`. Avoid `db:reset`: it discards local data. This restored local stack had a pre-existing `20260929104413_full_schema` ledger entry without a matching file or recoverable statements. Its version and name were recorded locally, then that orphaned history entry was reverted with the local CLI; no schema or user data changed. The local ledger still lacks many older migration versions, so normal CLI migration-up remains blocked. M12 migrations, including the final read optimization, were applied transactionally to this local stack and ledgered with the local CLI. Reconcile each target environment's schema and ledger before release; never replay the missing older files or assume this local repair applies to production.

If inbox reads fail, check API health and the task RPC outcome before retrying. An unavailable source row is title-free; a permission loss removes it. Do not clear routing/audit rows to resolve an outage. For a stale command, reload the task and resubmit with its new route/source revision and a new idempotency key. Exact retries use the original key and payload. Inspect group membership, absence expiry, source access, and product archive state for unresolved assignments.
