## Architecture and contract references

The System Health functional screen renders `apps/web/app/_features/support-diagnostics/support-diagnostics.tsx`. `SupportDiagnosticsGateway` in `support-diagnostics.gateway.ts` uses the authenticated transport with outgoing and incoming schemas. Feature-first contracts live in `packages/contracts/src/support-diagnostics/schemas/` and `/types/`; trusted wire types derive from `z.output`.

`SupportDiagnosticsController` parses body/query/path and successful JSON responses under `/api/v1/system/diagnostics`. It requires the administrator base role and `can_export_system_health`. `SupportDiagnosticsUseCases` owns consent/access policies and the repository, token, archive and artifact ports. Feature infrastructure adapters implement those ports; `DiagnosticWorker` owns bounded generation and reviewed cleanup. The API has no direct database calls in pages/controllers. Existing private ZIP behavior is retained through an audit-path compatibility re-export of `common/archive/stored-zip.ts`.

Consent, publication, inspection authorization, grant issuance/redemption and cleanup use transactional M13 audit receipts. Generic audit redaction and best-effort `AuditService.log()` retain their established behavior. Tenant exports receive closed disclosure/hash/retention metadata and exclude diagnostic section bytes. Retained bytes are protected generated storage. The [design](m15-04-support-diagnostics.md), [rollout/rollback runbook](m15-04-runbook.md), and [load evidence](m15-04-load-results.md) describe the boundaries and operating constraints.

## Final boundary regressions and memory probe

A successful infrastructure retry now clears its earlier failure code when publishing a ready artifact. A current-version cancellation cannot rewrite a reviewed cleanup workflow; exact command replay remains idempotent. Both transitions have real SQL regressions. Cleanup claims use their own parsed contract so a job cancelled before collection can finish its reviewed cleanup with no artifact path. The [real pathless-cleanup receipt](evidence/m15-04/pathless-cleanup-proof.json) confirms zero Storage removals and a durable deleted tombstone through the production repository and worker.

The [maximum-row memory probe](evidence/m15-04/memory-worker-proof.json) generated all three categories from 5,001 visible source events, emitted the bounded 5,000 rows and a fixed row-limit omission, and verified a 559,593-byte ZIP. Generation took 246.3 ms in this single local warm-context run. Sampling every 10 ms plus explicit stage hooks measured a 2.09 MiB incremental RSS peak and a 10.46 MiB maximum simultaneous heap-plus-external increment, below the 64 MiB working-memory budget. The already initialized Nest process had a roughly 331 MiB RSS baseline: this is an incremental workload measurement, not a 64 MiB total-process guarantee, continuous stress test or proof that sampling captures every transient allocation.
